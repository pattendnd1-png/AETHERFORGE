# ForgeHX v0.2 Universal Device Discovery + NGENUITY-Style UI Design

**Date:** 2026-08-14  
**Status:** Approved design, written specification  
**Target:** Arch Linux / Arch-derived x86-64 Linux, Wayland/X11, PipeWire/WirePlumber  
**Version:** 0.2.0

## 1. Goal

ForgeHX v0.2 expands the v0.1 HyperX-only HID discovery model into a universal Linux peripheral inventory while keeping the main application HyperX-first. The GUI is rebuilt around the newest-generation Windows HyperX NGENUITY design language: a dark charcoal shell, HyperX-red interaction accents, left navigation, large device presentation, contextual device tabs, profile controls, and card/slider-based settings.

ForgeHX branding and original artwork remain distinct. The software must not copy proprietary HyperX images, icons, logos, or bundled NGENUITY assets.

## 2. Non-Goals and Safety Boundaries

v0.2 does **not** send undocumented vendor-specific packets to arbitrary devices merely because they are detected.

Vendor-specific writes for lighting, DPI, bindings, firmware, hardware EQ, microphone DSP, or other proprietary features require an explicitly registered and verified ForgeHX device driver. Unknown devices remain diagnostic-only unless Linux exposes a safe generic control surface.

Firmware flashing remains disabled in v0.2.

ForgeHX may provide generic controls through stable Linux interfaces such as PipeWire/WirePlumber, sysfs power/battery metadata, and standard HID/USB descriptors without promoting the device to a vendor-specific driver.

## 3. Product Experience

### 3.1 Main Navigation

The left navigation rail contains:

- **Home** — HyperX-focused connected-device dashboard.
- **Devices** — HyperX devices and their device-specific workspaces.
- **Profiles** — persistent ForgeHX profiles.
- **All Devices** — full-system Device Manager for relevant USB/HID/audio peripherals.
- **Settings** — daemon status, discovery refresh/auto-refresh controls, diagnostics, and application preferences.

Connected HyperX devices are also shown as compact items in the navigation rail for direct access.

### 3.2 Home

Home prioritizes HyperX hardware. Each logical physical device is shown once, even when the hardware exposes multiple USB/HID interfaces.

Each card shows:

- product name;
- device class;
- support status;
- high-level capabilities;
- connection state;
- optional battery/state metadata when safely available.

Selecting a card opens the device workspace.

### 3.3 Device Workspace

A HyperX device workspace uses a large presentation region with an original ForgeHX-rendered silhouette/placeholder rather than copied HyperX artwork. The background uses a dark graphite gradient with restrained red accent lighting.

Below or adjacent to the presentation region, contextual tabs are generated from the device's capabilities. Available tab names are:

- Overview
- Lights
- Keys
- Assignments
- Performance
- DPI
- Audio
- Microphone
- EQ
- Profiles
- Doctor

Unsupported tabs are not shown.

Controls use cards, sliders, segmented selectors, color controls, profile chips, status pills, and compact metadata blocks instead of diagnostic grids as the primary interface.

### 3.4 All Devices / Device Manager

All Devices exposes every relevant peripheral ForgeHX can enumerate through its discovery sources, regardless of vendor.

Each physical device shows:

- device name;
- manufacturer/vendor family;
- device class;
- support level;
- safe generic controls, when available;
- VID/PID when applicable;
- serial when exposed;
- constituent interfaces/endpoints;
- Linux device path(s);
- attached ForgeHX driver, if any;
- diagnostics action.

The screen supports filtering by vendor, device class, and support level.

Non-HyperX hardware is visible here but does not clutter the HyperX-first Home screen.

## 4. Support Levels

Every logical physical device receives exactly one support level:

1. **Fully Supported** — a verified ForgeHX driver provides the expected vendor-specific controls for that device family.
2. **Partially Supported** — a verified ForgeHX driver exists but only some device-specific functions are implemented.
3. **Generic Controls** — no vendor-specific driver, but ForgeHX can safely control the device through Linux-standard interfaces such as PipeWire/WirePlumber.
4. **Diagnostic Only** — the device can be enumerated and inspected, but ForgeHX has no safe state-changing control path.
5. **Unavailable** — the device is known but access is blocked, disconnected, or an expected system interface is unavailable.

The daemon calculates the support level. The GUI only renders the daemon's result and cannot override it.

### 5.1 Core Types

  - `Logitech`
  - `Corsair`
  - `Razer`
  - `SteelSeries`
  - `Generic(String)`
  - `Unknown`

- `DeviceClass`
  - `Keyboard`
  - `Mouse`
  - `Headset`
  - `Microphone`
  - `Controller`
  - `Webcam`
  - `Mousepad`
  - `Monitor`
  - `AudioInterface`
  - `UsbAudio`
  - `GenericHid`
  - `Other`

- `SupportLevel`
  - `FullySupported`
  - `PartiallySupported`
  - `GenericControls`
  - `DiagnosticOnly`
  - `Unavailable`

- `ConnectionKind`
  - `Usb`
  - `Hid`
  - `Audio`

- `DeviceInterface`
  - source kind;
  - path;
  - VID/PID when known;
  - interface number;
  - HID usage page/usage when applicable;

`DeviceInfo` is extended with:

- `vendor_family`;
- `device_class`;

- `generic_capabilities: Vec<Capability>`;
- optional battery percentage/state metadata;
- existing verified protocol/driver identity.

The existing stable `DeviceId` remains the logical-device key.

### 5.2 Capabilities

Existing capabilities remain valid and are extended with safe generic capabilities where needed:

- Diagnostics
- Lighting
- Dpi
- Bindings
- Audio
- Microphone
- Eq
- BatteryStatus
- Volume
- Mute

A capability is not sufficient to authorize a vendor write. The daemon must also confirm that the selected device driver owns the capability or that the capability is serviced by a generic Linux backend.

## 6. Discovery Architecture

### 6.1 Discovery Sources

`forgehx-device` is split into focused modules:

- `hid.rs` — enumerate all HIDAPI descriptors without HyperX filtering.
- `usb.rs` — enumerate `/sys/bus/usb/devices` for visible USB devices/interfaces that may not expose HID endpoints.
- `classify.rs` — vendor and device-class inference from VID/PID, descriptor strings, HID usage metadata, and USB interface class/subclass/protocol.
- `group.rs` — merge descriptors/interfaces into logical physical devices.
- `drivers.rs` — attach verified ForgeHX vendor drivers.
- `doctor.rs` — diagnostic report production.

Audio nodes remain enumerated by `forgehx-audio`, then the daemon associates compatible PipeWire/WirePlumber nodes with logical devices when identity metadata permits. Unmatched audio nodes may appear as standalone logical audio devices in All Devices.

### 6.2 Grouping Rules

Interfaces are grouped into one physical device using strongest available identifiers in this order:

1. same non-empty serial + VID + PID;
2. same USB parent sysfs path + VID + PID;
3. deterministic normalized descriptor identity when neither serial nor parent identity is available.

Grouping must never merge two simultaneously connected devices solely because they share a model VID/PID.

The grouped logical device receives all constituent interfaces and the union of read-only metadata.

### 6.3 HyperX Identification

HyperX recognition uses multiple signals instead of one vendor-ID filter:

- known HyperX/Kingston/HP-HyperX VID/PID records;
- product/manufacturer branding;
- explicit verified-driver match;
- composite-interface association with an already recognized physical HyperX device.

Ordinary HP hardware must not be classified as HyperX without additional HyperX evidence.

### 6.4 All-Device Enumeration

The daemon keeps both views:

- `hyperx_devices`: logical devices classified as HyperX for Home/Devices;
- `all_devices`: all relevant logical devices for Device Manager.

IPC commands expose these separately so the GUI does not reimplement filtering rules.

## 7. Driver Registry and Write Authorization

Each verified vendor driver declares:

- driver ID and human-readable name;
- matching predicate or VID/PID set;
- supported capabilities;
- support completeness;
- state-changing operations it implements.

Generic Linux controls are provided by explicit generic backends, not by the vendor-driver registry.

Before every state-changing command the daemon performs:

1. locate logical device;
2. confirm requested capability exists;
3. select either the verified device driver or permitted generic backend;
4. reject the operation if neither path owns the capability;
5. execute only through the selected owner.

The GUI cannot send a raw HID packet command. No IPC command for arbitrary vendor writes is introduced.

## 8. Audio and Generic Controls

`forgehx-audio` broadens from HyperX-name filtering to all PipeWire/WirePlumber nodes required by Device Manager.

Safe generic controls include:

- output volume;
- input volume;
- mute/unmute;
- identification of source/sink kind;
- association with logical USB audio hardware when metadata provides a stable match.

Generic controls are available to HyperX and non-HyperX devices equally when the Linux audio stack exposes them.

Hardware/vendor EQ is not treated as generic. Software EQ is out of v0.2 scope unless already represented by an existing verified backend.

## 9. IPC Changes

The IPC protocol version is incremented for the v0.2 schema.

New/changed commands include:

- `ListHyperxDevices`
- `ListAllDevices`
- `RefreshDevices`
- `Doctor { device_id }`
- existing profile and state-changing commands updated to consume the expanded `DeviceInfo` model.

`ListDevices` may be retained as a compatibility alias for `ListHyperxDevices` during v0.2, but new clients use the explicit commands.

`Reply::Devices` remains the common serialized device-list reply unless separate reply names improve type clarity during implementation.

## 10. Daemon Runtime Behavior

The daemon is the single source of truth for inventory and permissions.

At startup it performs a full discovery pass and caches logical devices. It then refreshes inventory periodically at a modest cadence and immediately when the GUI/CLI explicitly requests refresh.

v0.2 may use polling instead of a dedicated udev event listener if that keeps the release dependable; the user-visible requirement is automatic device appearance/disappearance without restarting ForgeHX.

Inventory replacement is atomic from client perspective: clients receive a coherent completed snapshot, never half-grouped intermediate interfaces.

## 11. GUI Architecture

The current single `main.rs` GUI is split into focused modules:

- `app.rs` — application state, daemon synchronization, selection.
- `theme.rs` — charcoal/red ForgeHX visual system and reusable spacing/text styles.
- `nav.rs` — navigation rail and compact device navigation.
- `home.rs` — HyperX dashboard cards.
- `device_page.rs` — device presentation and capability-driven tabs.
- `all_devices.rs` — device manager, filters, support-state cards.
- `profiles.rs` — profile page.
- `settings.rs` — daemon/discovery/status settings.
- `widgets.rs` — support pills, metric cards, section headers, control cards.

The GUI remains `egui/eframe` to avoid replacing the v0.1 desktop stack.

### 11.1 Theme Tokens

The UI uses named tokens rather than scattered literal colors:

- `BG_APP`: near-black charcoal;
- `BG_NAV`: slightly darker rail;
- `BG_PANEL`: graphite panel;
- `BG_CARD`: raised charcoal;
- `ACCENT`: ForgeHX red inspired by the selected NGENUITY schema;
- `TEXT_PRIMARY`: near-white;
- `TEXT_SECONDARY`: cool gray;
- `STATUS_OK`, `STATUS_WARN`, `STATUS_BLOCKED`: semantic status colors.

Exact RGB values belong in `theme.rs` and may be tuned during implementation. The specification does not require pixel-for-pixel cloning.

### 11.2 Original Device Visuals

Until model-specific original silhouettes are authored, ForgeHX renders class-based vector-style placeholders using egui primitives. The placeholder must visually distinguish keyboard, mouse, headset, microphone, controller, webcam, and generic device classes.

No downloaded HyperX product photo is bundled into the application.

## 12. CLI Changes

CLI behavior becomes explicit:

- `forgehx list` — HyperX-first logical device list, preserving familiar v0.1 behavior.
- `forgehx list --all` or `forgehx devices all` — all-device inventory.
- `forgehx doctor [device] --json` — diagnostic report for logical device including grouped interfaces.
- `forgehx daemon refresh` — force inventory refresh.

Existing RGB/DPI/audio/profile commands continue to pass through daemon capability authorization.

## 13. Error Handling

Discovery failures are isolated by source where possible:

- HID failure does not erase valid USB/audio inventory if those sources succeed.
- malformed sysfs entries are skipped with diagnostics rather than crashing discovery.
- unavailable PipeWire/WirePlumber marks generic audio controls unavailable but does not hide HID/USB devices.
- permission failures map to `SupportLevel::Unavailable` when they prevent meaningful access.

The daemon returns structured IPC errors for unsupported or unauthorized writes.

The GUI presents concise user-facing errors and keeps detailed diagnostics in Doctor/Settings rather than flooding the main device page.

## 14. Testing Requirements

All production behavior follows test-first development.

Required unit/integration coverage includes:

- HID enumeration no longer filters non-HyperX devices.
- HP devices are not classified HyperX without HyperX evidence.
- known branding/VID evidence classifies HyperX correctly.
- two interfaces with one serial/USB parent group into one logical device.
- two physical devices with same VID/PID but different serials remain separate.
- capability union across grouped interfaces is deterministic.
- support-level calculation follows the five-state model.
- unknown device vendor writes are rejected.
- generic audio volume/mute routes through the generic audio backend.
- all-device IPC returns non-HyperX devices.
- HyperX IPC excludes unrelated devices.
- GUI tab list is derived from capabilities.
- All Devices filters by vendor/class/support state.
- IPC JSON round-trips after schema changes.

Because the current ChatGPT container previously lacked Cargo, package handoff must not claim compilation success unless fresh `cargo test --workspace` and `cargo build --workspace --release` commands actually run successfully in the active environment.

## 15. Packaging and Upgrade

Workspace version becomes `0.2.0`.

The Arch package updates to `pkgver=0.2.0` with an incremented `pkgrel` starting at `1` for the release source.

The package continues to install:

- `forgehx-daemon`;
- `forgehx` CLI;
- `forgehx-gui`;
- systemd user service;
- udev permissions/rules;
- desktop entry and icon/branding resources created for ForgeHX.

The v0.1 profile directory and profile schema remain readable unless a schema change is strictly required. If profile schema migration is needed during implementation, migration must be deterministic and tested.

## 16. Acceptance Criteria

ForgeHX v0.2 is ready for package handoff when all of the following are true:

1. A connected non-HyperX HID peripheral appears in All Devices.
2. A connected HyperX device appears in Home/Devices and All Devices.
3. Composite/multi-interface hardware is shown once as a logical device when stable grouping evidence exists.
4. The UI visibly follows the selected newest-generation NGENUITY design language while using ForgeHX branding and original visuals.
5. HyperX Home stays uncluttered by unrelated brands.
6. Safe generic PipeWire volume/mute controls can be exposed for non-HyperX audio hardware.
7. Unknown devices cannot receive vendor-specific state-changing writes.
8. Support state is visible and generated by the daemon.
9. Device inventory updates automatically without restarting the application.
10. Device Doctor reports the grouped interfaces used to identify a logical device.
11. The Arch source/build kit contains version 0.2.0 metadata and passes the existing package-layout checks updated for the new release.
12. If a Rust toolchain is available, `cargo test --workspace` and `cargo build --workspace --release` both exit successfully before the build is described as compiled or passing.

## 17. Implementation Direction

The implementation should evolve the existing v0.1 crates rather than restart the project. The core sequencing is:

1. expand core device/support types and IPC;
2. replace HyperX-only discovery with universal discovery and grouping;
3. attach generic audio controls and verified-driver support calculation;
4. update daemon inventory/refresh behavior;
5. update CLI;
6. rebuild the GUI into the new modular NGENUITY-style ForgeHX experience;
7. update tests, packaging, and release kit.

The daemon remains the security boundary throughout the upgrade.
