# ForgeHX 0.5.0 HyperX Peripheral Platform Design

## Status

Approved architectural direction for ForgeHX 0.5.0.

## Release identity

ForgeHX 0.5.0 is a full semantic-version release. The canonical release identity is `0.5.0` with Arch `pkgrel=1`.

Canonical public artifacts:

- `ForgeHX-0.5.0-source.tar.gz`
- `ForgeHX-0.5.0-Arch-BuildKit.tar.gz`
- built Arch package: `forgehx-0.5.0-1-x86_64.pkg.tar.zst`

Do not use RC labels, revision suffixes, `rN` suffixes, duplicate archive names, or competing release identities.

## Objective

Extend ForgeHX from a mouse/microphone-focused HyperX control application into a HyperX-first Linux peripheral platform covering programmable/electronic current and legacy HyperX hardware while preserving capability-level honesty and exact-device write safety.

Passive accessories that expose no programmable interface remain inventory-only and do not receive synthetic controls.

## Product scope

ForgeHX 0.5.0 introduces first-class support architecture for:

- keyboards
- mice
- headsets and earbuds
- microphones
- game controllers
- webcams
- monitors
- illuminated mousepads and lighting accessories
- USB audio endpoints associated with supported HyperX devices
- shared firmware inventory/validation/update infrastructure

The existing `DeviceClass` model remains authoritative. New subsystems attach to existing classes rather than inventing a second parallel inventory model.

## Architectural choice

Use a shared peripheral framework plus protocol-family crates.

Do not create one giant HyperX switch statement, and do not create isolated one-off code paths for every product when multiple products share transport/protocol behavior.

Target crate layout:

```text
ForgeHX Core
├── forgehx-device            # inventory, grouping, exact HID/USB identity
├── forgehx-keyboard          # HyperX keyboard families
├── forgehx-mouse             # Pulsefire/Haste/Saga families
├── forgehx-headset           # Cloud/headset/earbud families
├── forgehx-microphone        # HyperX mic hardware controls
├── forgehx-dsp               # input-only microphone DSP
├── forgehx-controller        # Clutch/controller families
├── forgehx-camera            # Vision/UVC controls
├── forgehx-display           # Armada/DDC-CI controls
├── forgehx-lighting          # mousepads/lighting-only devices
├── forgehx-firmware          # shared firmware framework/adapters
├── forgehx-audio             # PipeWire/WirePlumber standard audio
├── forgehx-openrgb           # OpenRGB capability fallback
├── forgehx-ratbag            # libratbag capability fallback
├── forgehx-daemon            # sole write authority / ownership routing
├── forgehx-ipc               # typed IPC client/server
├── forgehx-cli               # command-line client
└── forgehx-gui               # NGENUITY-style UI
```

## Core peripheral descriptor

Every recognized HyperX model/family must be represented by data, not scattered name checks.

The shared descriptor must be able to express:

- canonical model ID
- canonical display name
- device class
- protocol family
- exact USB VID/PID identities
- optional wired/wireless/Bluetooth transport variants
- optional HID interface/usage-page constraints
- name aliases for metadata-only recognition
- expected standard Linux subsystem (hidraw, evdev, PipeWire, V4L2, DDC/CI, Bluetooth)
- capability limits/ranges
- native capability set
- safe fallback capability set
- firmware adapter ID
- completeness/support qualification

Exact hardware identity and name-only recognition must remain distinct states.

### Name-only rule

A product-name or alias match may supply model metadata and UI labels, but **must never grant proprietary/native write authority**. Native writes require an exact verified hardware identity plus the protocol/interface constraints defined for that model.

Name matching must continue to prefer exact normalized names and the longest/specific alias so variants such as Haste 2 Mini/Core/S/Pro cannot collapse into the generic Haste entry.

## Capability ownership

There is exactly one owner for each capability at a time.

Priority remains:

1. `ForgeHxNative`
2. `ForgeHxDsp` (microphone input processing only)
3. `LinuxStandard`
4. `OpenRgb` / `Ratbag`
5. `Diagnostic`

A backend may own only a capability it can actually execute for that exact device.

Support state is derived from real capability coverage, never from product recognition alone:

```text
Diagnostic Only
Recognized
Linux Standard Supported
Partially Supported
Fully Supported
```

`Fully Supported` means every capability ForgeHX advertises for that model has a working owner and handler.

## Keyboard subsystem

### Family targets

The registry must accommodate current and legacy HyperX keyboard families including, as protocol evidence is available:

- Alloy Origins
- Alloy Origins Core
- Alloy Origins 60
- Alloy Origins 65
- Alloy Elite / Elite RGB / Elite 2
- Alloy FPS / FPS RGB
- Alloy Rise / Rise 75 / wireless variants
- Origins 2 families
- Eve families
- MKW100
- future HyperX keyboard variants through the same registry without daemon rewrites

### Keyboard capabilities

Common keyboard capabilities:

- per-key RGB where hardware supports it
- zone RGB on zone-based models
- static/breathing/wave/cycle/trigger effects where verified
- brightness
- key reassignment
- keyboard shortcuts
- media functions
- macros
- Game Mode
- Windows-key lock / configured disabled keys
- onboard profiles
- active profile
- profile persistence
- polling/report rate where exposed
- battery/charging state on wireless models
- 2.4 GHz/Bluetooth/USB transport state where observable
- firmware inventory and model-gated firmware update

Hall-effect/adjustable-actuation models may additionally expose, only when verified:

- per-key actuation distance
- global actuation preset
- Rapid Trigger enable
- Rapid Trigger press/release sensitivity/reset distance
- analog/continuous key information if the protocol genuinely exposes it

ForgeHX must not emulate these as software-only keyboard settings and label them as onboard hardware controls.

### Keyboard Linux fallback

Normal typing remains Linux HID/evdev functionality regardless of ForgeHX native support.

OpenRGB may own lighting when deterministic device matching exists and the native ForgeHX lighting driver is absent.

Software key remapping may be offered separately only if clearly labeled as Linux/software remapping rather than onboard configuration.

## Mouse subsystem

Retain the 0.4.2 mouse model registry, Haste Wireless native DPI/polling, Saga Pro verified native capabilities, OpenRGB/ratbag fallback routing, specificity-aware name matching, and exact-write safety.

0.5.0 continues promotion of legacy Pulsefire native capabilities only from verified protocol evidence. Priority families:

- Surge
- FPS Pro / Core
- Dart
- Raid
- wired Haste variants
- Haste 2 variants
- Saga/Saga Pro variants

Lighting packets may be promoted independently from DPI/polling/buttons/macros when only lighting has verified protocol evidence.

## Headset and earbud subsystem

### Family targets

The registry must accommodate current and legacy Cloud/HyperX audio families such as:

- Cloud II families
- Cloud III / Cloud III Wireless / Cloud III S families
- Cloud Alpha / Alpha Wireless / Alpha 2 families
- Cloud Flight families
- Cloud Stinger families
- Cloud MIX families
- HyperX earbuds / MIX Buds families
- future HyperX USB/wireless headsets

### Standard audio layer

PipeWire/WirePlumber remains the authoritative standard Linux audio transport for:

- playback volume
- microphone source volume
- mute
- node discovery
- routing

### Native headset capabilities

Model-specific native adapters may own:

- hardware sidetone
- mic monitoring
- chat/game balance
- base-station controls
- battery percentage
- charging state
- wireless connection state
- power/sleep timeout
- ANC
- ambient/transparency mode
- RGB/status LEDs
- hardware EQ if genuinely onboard
- firmware inventory/update

ForgeHX must not claim proprietary DTS or other licensed processing as native ForgeHX functionality. Open/native spatial processing, if later added, must be separately labeled.

## Microphone subsystem

Retain the 0.4.x input-only architecture:

```text
Physical HyperX Mic
  -> ForgeHX input DSP
  -> ForgeHX Processed Mic (Audio/Source)
  -> recording/voice applications
```

Do not create a ForgeHX playback DSP sink.

Retain:

- gain/mute
- hardware monitoring/sidetone where verified
- polar pattern where verified
- lighting/status LEDs where verified
- input DSP: HPF, noise suppression, gate/expander, EQ, compressor, de-esser, limiter, output gain
- profiles
- meters
- virtual processed mic
- firmware manager

Expand the microphone model registry without weakening the exact-protocol rule.

## Controller subsystem

HyperX controllers use Linux evdev/hidraw as the standard input base.

Model-specific native capabilities may include:

- button remapping/onboard assignments
- rear-button assignments
- stick calibration
- stick dead zones
- trigger calibration/dead zones
- trigger-lock state if electronically exposed
- rumble strength/test
- RGB
- headset/audio state where a controller exposes a USB audio interface
- local profiles
- firmware inventory/update

ForgeHX must not intercept normal controller gameplay input merely to provide configuration.

## Camera subsystem

HyperX webcams should use V4L2/UVC first.

Standard camera capabilities may include:

- resolution/frame-rate enumeration
- exposure / auto exposure
- gain
- autofocus / manual focus
- white balance / auto white balance
- contrast
- saturation
- sharpness
- zoom
- anti-flicker/power-line frequency
- low-light compensation when exposed
- privacy state when exposed

Model-specific native control is allowed only for features absent from UVC/V4L2 and backed by verified protocol evidence.

Firmware inventory/update uses the shared firmware framework.

## Display subsystem

HyperX monitors use DDC/CI first through a standard Linux backend.

Standard controls may include:

- brightness
- contrast
- input/source selection
- power state where supported and safe
- common VCP controls

Model-specific USB controls are optional extensions only when verified. ForgeHX must not replace standard DDC/CI with proprietary HID writes when the standard mechanism works.

## Mousepad and lighting accessory subsystem

Illuminated HyperX mousepads/lighting-only devices are represented as `Mousepad` or appropriate lighting accessory classes.

Capabilities may include:

- static RGB
- zones
- brightness
- supported effects
- profiles/persistence where hardware provides them

OpenRGB remains the preferred fallback until a native protocol is verified.

## Shared firmware subsystem

Generalize the 0.4.x mic firmware manager into a device-class-neutral framework while keeping model-specific update adapters.

### Firmware framework responsibilities

- read/report installed firmware when available
- stage a firmware payload immutably
- compute and display SHA-256
- validate package structure and compatibility
- validate exact model / VID / PID / hardware revision
- validate version policy
- journal every update transaction
- detach dependent runtime processing when required
- invoke only the exact model adapter
- wait for re-enumeration/recovery states
- verify post-update firmware/version
- restore device profile/state only after successful verification

### Adapter families

```text
HyperXMicFirmwareAdapter
HyperXKeyboardFirmwareAdapter
HyperXMouseFirmwareAdapter
HyperXHeadsetFirmwareAdapter
HyperXControllerFirmwareAdapter
HyperXCameraFirmwareAdapter
```

Additional adapters may be added for displays/accessories only where a safe official/verified update transport exists.

### Firmware hard rules

- no generic raw firmware flashing command
- no arbitrary `.bin` write path
- no firmware bytes transported through a generic HID IPC request
- no firmware payload bundled inside ForgeHX release artifacts
- no model adapter may become `UpdateCapable` without verified update and recovery behavior
- exact hardware revision mismatch is a hard refusal
- hash/package validation failure is a hard refusal
- device disconnect during update produces a journaled recovery state, never silent success
- downgrades require explicit support by that adapter and an explicit user action

## Daemon authority

`forgehx-daemon` remains the sole process authorized to execute configuration writes.

GUI and CLI remain IPC clients. They do not open hidraw devices directly, do not write firmware directly, and do not independently manage backend ownership.

Device-specific crates expose typed operations; the daemon validates ownership and routes them.

## IPC evolution

ForgeHX 0.5.0 may advance the IPC protocol from v6 to v7 when new typed keyboard/headset/controller/camera/display requests or replies are added.

Compatibility floor remains protocol v2 unless a concrete incompatibility forces a documented change.

For older compatible clients, inventory/status projection must remove capability/backend/enum values introduced after that client's protocol version. Older clients must never fail deserialization because a new peripheral class capability leaked into a legacy reply.

New 0.5.0 commands must fail with `protocol_mismatch` against older daemons rather than silently falling back.

## CLI architecture

CLI commands should follow class-first typed namespaces, for example:

```text
forgehx keyboard state <device>
forgehx keyboard lighting ...
forgehx keyboard profile ...
forgehx keyboard firmware ...

forgehx headset state <device>
forgehx headset sidetone ...
forgehx headset anc ...
forgehx headset firmware ...

forgehx controller state <device>
forgehx camera state <device>
forgehx display state <device>
```

Shared firmware commands may delegate to the same firmware service while remaining discoverable from each device-class namespace.

## Packaging and Linux integration

ForgeHX remains Arch/Arch-derived Linux first.

Expected standard integrations/dependencies as features land:

- PipeWire / WirePlumber
- OpenRGB
- libratbag
- hidapi linux-native
- libevdev or equivalent standard input access where required
- V4L2 userspace tools/libraries where required
- ddcutil/libddcutil where required
- BlueZ integration for Bluetooth metadata only where it materially improves device status

Dependencies must be added only when the corresponding production feature is implemented; do not pre-install a large dependency stack for unimplemented peripherals.

Udev rules must prefer exact verified VID/PID identities. Do not grant blanket writable access to all HP (`03f0`) hidraw devices.

## Security and failure behavior

- unknown HID writes remain blocked
- unknown device variants stay diagnostic/metadata-only
- exact capability failure degrades that capability, not the entire peripheral
- backend ambiguity is an error; never guess between two devices
- firmware failure never reports success without post-update verification
- raw debugging output may inspect descriptors/reports only where safe; generic arbitrary output reports remain outside normal IPC
- no driver may claim a capability merely because a similarly named device has it

## Testing strategy

Every protocol family must have packet encoder/decoder tests for known packets before native writes are routed.

Minimum regression coverage:

- exact VID/PID matches resolve to the intended model
- name-only matches resolve to the most specific model but do not grant native write ownership
- unrelated HP devices never inherit HyperX native capabilities
- capability ownership priority is deterministic
- missing fallback backends never own capabilities
- protocol compatibility projections hide newer enum/capability values from older clients
- UI control visibility follows capability state
- firmware validation rejects model/revision/hash mismatches
- firmware transaction journal survives daemon restart
- package guards verify canonical 0.5.0 naming and no bundled firmware payloads

Hardware qualification remains per physical model/transport. Evidence from one device or architecture does not qualify another model.

## Implementation order

### Phase 1 — Peripheral platform foundation

- generalized model descriptor/registry
- new capability types grouped by class
- IPC v7 compatibility/projection if required
- capability-gated GUI/CLI scaffolding
- package/test guards for 0.5.0

### Phase 2 — Keyboards

- Linux-standard keyboard inventory
- current/legacy HyperX model registry
- OpenRGB lighting fallback
- first verified native protocol family
- profiles/key assignment/macro architecture
- Hall-effect capability model
- keyboard firmware adapter framework

### Phase 3 — Headsets/earbuds

- PipeWire pairing/identity
- wireless/battery metadata
- verified native controls such as sidetone/ChatMix/ANC where available
- headset firmware adapters

### Phase 4 — Controllers and camera

- evdev controller configuration model
- V4L2/UVC camera controls
- model registries
- firmware adapters where verified

### Phase 5 — Displays and lighting accessories

- DDC/CI display backend
- mousepad/lighting accessory registry
- OpenRGB fallback and selective native promotion

### Phase 6 — Continue mouse-native promotion

Continue legacy/current HyperX mouse protocol families in parallel without weakening exact-device safety.

## 0.5.0 completion definition

ForgeHX 0.5.0 is complete when:

- the shared peripheral framework is authoritative
- keyboard support is first-class in daemon/IPC/CLI/GUI
- all in-scope current/legacy HyperX peripheral families can be represented and recognized without daemon-specific name hacks
- standard Linux backends provide real controls where available
- verified native capabilities override fallbacks capability-by-capability
- firmware is generalized across device classes with no generic raw flasher
- older IPC clients are protected from new enum/capability values
- canonical source/build artifacts use only the `0.5.0` version identity
- no device is labeled Fully Supported unless every advertised capability has a working handler

This does not require every proprietary HyperX protocol to be reverse-engineered before 0.5.0 ships. It requires a complete, honest platform in which every peripheral can be represented and progressively promoted without duplicate implementations, unsafe guessed writes, or false support claims.
