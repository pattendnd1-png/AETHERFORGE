# ForgeHX v0.3 Control Backends + Native Driver Promotion Design

**Date:** 2026-08-14
**Status:** Approved design, written specification
**Target:** Arch Linux / Arch-derived x86-64 Linux, Wayland/X11, PipeWire/WirePlumber
**Version:** 0.3.0

## 1. Goal

ForgeHX v0.3 turns the v0.2 universal inventory into a functional control plane. It keeps ForgeHX as the single user-facing application and daemon authority while combining three classes of control implementation:

1. native verified Rust ForgeHX drivers;
2. stable Linux-standard interfaces such as PipeWire/WirePlumber and sysfs;
3. mature external compatibility backends such as OpenRGB and ratbagd/libratbag.

The long-term goal remains native ForgeHX drivers. Compatibility backends exist to provide useful control coverage immediately and are automatically superseded capability-by-capability when a verified native ForgeHX implementation becomes available.

## 2. Core Safety Rule

Every state-changing capability has exactly one selected owner at a time.

Backend priority is:

1. **ForgeHX Native** — verified device-specific Rust driver;
2. **Linux Standard** — stable kernel/PipeWire/WirePlumber/sysfs interface;
3. **Compatibility Backend** — OpenRGB for lighting or ratbagd/libratbag for gaming-mouse controls;
4. **Diagnostic Only** — no safe write path exists.

Detection alone never authorizes a write. A capability must be advertised by a backend, selected by the daemon, and authorized for the exact logical device before a state-changing command is executed.

The GUI cannot select a lower-priority backend to bypass a native driver. It may display the selected owner and availability of fallbacks for diagnostics.

## 3. External Interface Baseline

### 3.1 OpenRGB

ForgeHX integrates with OpenRGB as a separate process through the OpenRGB network SDK. It does not link against OpenRGB libraries or import OpenRGB source code.

The adapter must:

- connect to localhost by default on TCP port `6742`;
- negotiate the OpenRGB SDK protocol version before requesting controller data;
- support SDK protocol versions `1..=5` with v5 as the preferred maximum;
- set client name to `ForgeHX`;
- enumerate controllers, modes, zones, LEDs, brightness and supported mode metadata exposed by the negotiated protocol;
- map OpenRGB controllers back to ForgeHX logical devices using vendor/product/name/serial/location hints where available;
- reject ambiguous matches instead of controlling the wrong physical device;
- expose lighting only when a unique match exists;
- subscribe or rescan when OpenRGB reports a device-list update;
- never ask OpenRGB to control a logical capability already owned by a native ForgeHX driver.

ForgeHX will ship a user service for the OpenRGB SDK server. The service owns background execution; ForgeHX does not assume `openrgb --server` forks itself.

### 3.2 ratbagd / libratbag

ForgeHX treats ratbagd as a separate system D-Bus service. The adapter does not link against libratbag internals.

The adapter must enumerate ratbagd devices and expose only capabilities reported by the device/profile objects, including where available:

- DPI/resolution slots;
- active/default resolution;
- report rate/polling rate;
- profiles;
- button assignments;
- macros/actions;
- mouse LEDs exposed by ratbagd.

Writes are capability-checked before execution. ForgeHX must preserve ratbagd's profile commit/dirty semantics and return an error if the backend rejects or cannot persist a requested change.

### 3.3 PipeWire / WirePlumber

Existing volume and mute control remains the standard Linux audio path.

v0.3 adds a ForgeHX EQ manager using PipeWire's parametric-equalizer module. EQ profiles are stored by ForgeHX and rendered as PipeWire-compatible files with:

- preamp in dB;
- enabled/disabled filters;
- filter type: peaking, low-shelf, high-shelf;
- center/corner frequency in Hz;
- gain in dB;
- Q factor;
- channel count and channel map where explicitly needed.

ForgeHX generates its own PipeWire drop-in and EQ data files under the user's configuration directory. It must only manage files bearing the ForgeHX namespace and must not rewrite unrelated PipeWire configuration.

Microphone gain, mute and routing continue through WirePlumber/PipeWire standard controls. Advanced microphone DSP that lacks a stable standard interface remains unavailable until a verified native driver or a dedicated ForgeHX DSP implementation exists.

## 4. Package Policy

The Arch package changes to version `0.3.0` and installs the compatibility stack required for the complete v0.3 experience.

Required runtime packages include:

- `openrgb`;
- `libratbag`;
- `pipewire-audio`;
- `wireplumber`;
- existing graphical/system dependencies from v0.2.

The package installs:

- the existing `forgehx-daemon.service` user service;
- a new `forgehx-openrgb.service` user service that runs the OpenRGB SDK server;
- ForgeHX PipeWire configuration templates/managed-directory documentation;
- unchanged udev rules for ForgeHX-native HID access.

ForgeHX does not replace ratbagd's packaged service. It relies on ratbagd's D-Bus/systemd activation model.

## 5. New Backend Crate

Add workspace crate `crates/forgehx-backends`.

Responsibilities:

- define backend-neutral control traits and backend health/status types;
- implement OpenRGB SDK client;
- implement ratbagd adapter;
- implement backend matching helpers;
- provide deterministic capability-owner selection inputs to the daemon;
- contain no GUI code and no raw native HyperX HID protocol code.

Proposed modules:

- `lib.rs` — public types and adapter facade;
- `backend.rs` — backend identifiers, health, errors, owned capabilities;
- `selector.rs` — priority and conflict resolution;
- `openrgb.rs` — SDK framing, negotiation, controller enumeration and writes;
- `ratbag.rs` — D-Bus adapter and gaming-mouse operations;
- `match_device.rs` — external-backend device matching.

## 6. Core Model Changes

### 6.1 Backend Identity

Add serializable `BackendKind`:

- `ForgeHxNative`
- `LinuxStandard`
- `OpenRgb`
- `Ratbag`
- `Diagnostic`

Add `CapabilityOwner` containing:

- `capability: Capability`;
- `backend: BackendKind`;
- `backend_device_id: Option<String>`;
- `verified: bool`;
- `writable: bool`;
- optional human-readable detail.

`DeviceInfo` gains `capability_owners: Vec<CapabilityOwner>`.

The existing capability collections remain for compatibility but are derived from owners rather than independently authorizing writes.

### 6.2 Extended Capabilities

Add, where not already present:

- `PollingRate`
- `Profiles`
- `MacroAssignments`
- `Eq`
- `AudioRouting`

Native-driver capability declarations remain explicit.

## 7. Backend Selection

For each logical device and capability, the daemon builds candidate owners and selects one using a deterministic pure function.

Priority score:

1. native verified driver;
2. Linux standard backend;
3. capability-specific compatibility backend;
4. diagnostic fallback.

Additional rules:

- a backend that is unhealthy cannot own a writable capability;
- an ambiguous external-device mapping is never writable;
- OpenRGB can own `Lighting`, not `Dpi`, `Bindings`, audio, or arbitrary vendor writes;
- ratbagd can own gaming-mouse capabilities it explicitly exposes;
- PipeWire/WirePlumber owns safe audio capabilities when a node is mapped;
- native drivers may own only capabilities declared by their verified registry entry;
- two backends must never execute the same state-changing capability for the same logical device.

Selection is recomputed after device refresh, backend reconnect, or driver promotion.

## 8. Native Driver Promotion

Native ForgeHX drivers remain in `forgehx-device` and implement a common driver contract.

Each driver declares:

- driver ID;
- match criteria;
- verified VID/PID/interface records;
- owned capabilities;
- read/query functions;
- state-changing operations;
- support completeness.

When a native driver begins owning a capability previously serviced by OpenRGB or ratbagd:

1. refresh inventory;
2. mark native candidate healthy/verified;
3. select native owner;
4. stop routing future writes to the fallback;
5. display `ForgeHX Native` in the GUI;
6. preserve profile intent so the same ForgeHX profile continues to apply.

No migration should require users to recreate their ForgeHX profile merely because the implementation backend changed.

## 9. OpenRGB Control Scope

The first OpenRGB adapter release supports:

- server health/protocol negotiation;
- controller enumeration;
- static color;
- per-zone color where the SDK exposes zones;
- per-LED color where the SDK exposes individually addressable LEDs;
- hardware modes exposed by controller mode metadata;
- speed and brightness when supported by the selected mode/protocol;
- device rescan;
- readable controller/mode/zone metadata for Device Doctor.

ForgeHX effects that require continuous animation may initially drive SDK LED updates from the daemon at a bounded refresh rate. The daemon must stop animation tasks when a device disconnects, ownership changes, or the profile changes.

## 10. Gaming Mouse Control Scope

The ratbag adapter first-release scope is:

- list supported ratbag devices;
- query profiles;
- select active profile when backend permits;
- query/set DPI resolution slots;
- query/set report rate when supported;
- query/set button assignments supported by ratbagd;
- query/set macros supported by ratbagd;
- query/set ratbag-exposed mouse LEDs;
- commit changes using the backend's required profile transaction semantics.

If ratbagd reports a capability unavailable for a device, ForgeHX must hide/disable that control instead of manufacturing a generic command.

## 11. EQ and Audio Profiles

`Profile` evolves to schema version 2 with migration from schema version 1.

New profile sections:

- `lighting` intent;
- `mouse` intent with DPI/report-rate/profile/button assignments;
- `audio` intent with volume/mute/routing;
- `eq` intent with preamp and filters;
- backend-neutral device selectors.

Profile values express desired behavior, not backend commands. The daemon translates profile intent through the currently selected capability owner.

Schema v1 profiles load unchanged and migrate in memory/default missing sections. Saving writes schema v2.

## 12. IPC v3

Bump `IPC_PROTOCOL_VERSION` to `3`.

Add commands/replies for:

- backend status list;
- capability-owner refresh/status;
- lighting controller metadata;
- set lighting mode/color/brightness/speed;
- mouse profile/DPI/report rate/button assignment actions;
- EQ profile list/get/save/delete/apply;
- unified profile apply;
- backend rescan.

No arbitrary raw OpenRGB packet, ratbag D-Bus method, shell command, or HID packet is exposed over IPC.

Every state-changing command is validated in the daemon against the selected `CapabilityOwner`.

## 13. GUI v0.3

Keep the v0.2 newest-NGENUITY-style shell and add functional controls.

### 13.1 Device Page

Each contextual tab shows a compact backend badge:

- `ForgeHX Native`
- `Linux / PipeWire`
- `OpenRGB`
- `libratbag`
- `Diagnostic`

The badge is informational. It does not allow manual unsafe backend selection.

### 13.2 Lighting

Lighting page provides:

- controller/mode selector;
- static color picker;
- zone/LED selector when available;
- brightness;
- effect speed;
- profile save/apply;
- support warning when the backend cannot map the device uniquely.

### 13.3 Mouse / Performance

Mouse pages provide:

- DPI stages;
- active/default DPI stage;
- polling/report rate;
- profile selector;
- button assignments/macros where exposed;
- mouse lighting if owned by ratbagd or OpenRGB/native driver.

### 13.4 Audio / EQ / Microphone

Audio pages provide:

- volume/mute;
- output/input association;
- EQ preset selector;
- preamp control;
- configurable parametric EQ bands;
- reset/bypass;
- per-device persistence;
- microphone level/mute/routing where available.

## 14. Backend Health and Failure Behavior

Every backend reports one of:

- `Ready`
- `Unavailable`
- `Disconnected`
- `PermissionDenied`
- `ProtocolMismatch`
- `AmbiguousDeviceMatch`
- `BackendError(String)`

Failure rules:

- backend failure must not crash the daemon;
- unavailable compatibility backend removes only the capabilities it owns;
- native or Linux-standard capabilities remain usable;
- active animations/tasks terminate cleanly on backend loss;
- GUI displays actionable status and retry/rescan controls;
- diagnostic logs never include arbitrary private file contents or unrelated process environment.

## 15. Tests

### 15.1 Pure Unit Tests

Tests must cover:

- capability-owner priority;
- rejection of unhealthy/ambiguous candidates;
- native promotion over OpenRGB/ratbag;
- OpenRGB packet header encode/decode;
- OpenRGB protocol negotiation boundaries;
- deterministic controller matching;
- ratbag capability parsing/model conversion;
- v1-to-v2 profile migration;
- EQ file rendering and validation;
- IPC protocol v3 serialization.

### 15.2 Integration Tests

Use deterministic fake servers/adapters where possible:

- fake OpenRGB TCP server for negotiation/enumeration/write tests;
- fake backend facade for daemon routing tests;
- no physical-device write tests in CI;
- backend command tests must verify that a lower-priority backend is not called when native owns the capability.

### 15.3 Arch Validation

On the user's Arch system:

```bash
cargo fmt --all -- --check
cargo test --workspace
cargo build --workspace --release
makepkg -f
```

Then runtime checks:

```bash
systemctl --user status forgehx-daemon.service
systemctl --user status forgehx-openrgb.service
systemctl status ratbagd.service
forgehx backend status
forgehx list --all
forgehx doctor --json
```

## 16. Packaging Acceptance Criteria

ForgeHX v0.3 is acceptable for package handoff when:

- workspace version is `0.3.0`;
- IPC protocol is `3`;
- profile schema is `2` with v1 migration tests;
- OpenRGB network adapter exists and never links/copies OpenRGB code;
- ratbag adapter exists through the service interface;
- PipeWire EQ manager only writes ForgeHX-owned configuration files;
- capability ownership is deterministic and daemon-enforced;
- GUI displays selected backend per functional tab;
- package depends on the v0.3 compatibility stack;
- OpenRGB service unit is included;
- static/package regression checks pass;
- Rust compile/test/package status is reported truthfully from the environment that actually runs those tools.

## 17. Explicit Non-Goals for v0.3

- firmware flashing;
- undocumented writes to unverified devices;
- claiming every device supported by detection is fully controllable;
- reproducing proprietary HyperX assets;
- replacing OpenRGB or libratbag internals wholesale in one release;
- kernel driver development;
- remote OpenRGB control exposed by default beyond localhost.

## 18. Research Baseline

The design was checked against the current OpenRGB SDK documentation, current OpenRGB Arch package, libratbag/ratbagd project documentation and Arch package, and current PipeWire parametric-equalizer documentation as of 2026-08-14.
