# OpenSanctuary v0.3.12 Seamless Battle.net Flow Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Route install, sign-in, update, and play through one testable preparation pipeline so OpenSanctuary remains the primary visible launcher.

**Architecture:** Add a pure preparation decision engine to `sanctuary-launcher`. `LauncherApp` converts current model/discovery/session state into a context, asks the engine for the next decision, and executes that decision using existing v0.3.11 software/network bridge functions. No duplicate process-launch path is introduced.

**Tech Stack:** Rust 2024 edition, egui/eframe, existing `sanctuary-launcher`, `sanctuary-battlenet`, existing thread/event bus.

**Spec:** `docs/superpowers/specs/2026-08-23-v0.3.12-seamless-battlenet-flow-design.md`

## Global Constraints
- Full semantic version update only: `0.3.11` → `0.3.12`; no revision/RC suffix.
- Preserve v0.3.11 software bridge and network bridge as canonical implementations.
- Never store or inject raw Blizzard passwords, 2FA codes, recovery codes, captcha responses, or security answers.
- Do not add proxying, DNS rewriting, TLS weakening, private Battle.net protocols, or proprietary asset redistribution.
- `cargo fmt --all -- --check`, `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, and release build remain the Arch-side compiler gate.
