# OpenSanctuary v0.3.12 Seamless Battle.net Flow Design

## Goal
Make the normal Diablo III experience originate and remain in OpenSanctuary, showing Battle.net only when Blizzard requires user interaction, while reusing the working v0.3.11 software and network bridges.

## Core flow
All install, sign-in, update, and play actions route through one preparation pipeline. The pipeline evaluates current network health, Battle.net software discovery, desktop session/process observation, Diablo III installation state, update state, and content readiness before deciding the next action.

Normal PLAY must remain on the Diablo III page. If the existing desktop session and game are ready, OpenSanctuary launches directly through the existing official bridge without switching to the Battle.net page. If Battle.net must be started in the background, OpenSanctuary starts it without forcing navigation. If Blizzard requires visible authentication or installation interaction, OpenSanctuary opens the integrated Battle.net surface and explains why.

## User-facing states
A new launcher-owned `SessionIntent` represents the user's desired outcome: `Install`, `SignIn`, `OpenClient`, or `Play`. A `PreparationDecision` represents the next action: `RepairNetwork`, `RepairSoftwareBridge`, `OpenDownloadPage`, `ShowBattleNetInteraction`, `WatchInstall`, `WaitForUpdate`, `VerifyGame`, `IndexContent`, `LaunchGame`, or `AlreadyRunning`.

The decision engine is pure and lives in `sanctuary-launcher`, making state transitions testable without spawning processes. `LauncherApp` executes the decision using existing bridge functions.

## Login behavior
OpenSanctuary never captures or stores Battle.net passwords, authenticator codes, recovery codes, captcha responses, or security answers. Sign-in uses the Blizzard-controlled Battle.net surface. Account identity hints remain non-secret.

## Install behavior
`INSTALL DIABLO III` starts the preparation pipeline. If Battle.net is missing, the existing official download-page path is used. If Battle.net is ready, the client is started/reused and the integrated Battle.net surface is shown only because Blizzard installation interaction is required. OpenSanctuary keeps watching for the Diablo III installation and resumes verify/index automatically when it appears.

## Play behavior
`PLAY` first rejects only a confirmed offline network bridge or active failure cooldown. It then refreshes discovery/session state. If Diablo III is already running, it reports RUNNING without launching another copy. If an update is active, it stays on the Diablo page and waits. If verification/indexing is needed, it starts those local stages. If the official game is ready, it launches through the existing bridge. Battle.net navigation is not forced unless authentication/user interaction is actually required.

## UI behavior
The Diablo III page gains a compact `Session status` line sourced from the preparation decision, e.g. `Ready to play`, `Starting Battle.net in background`, `Sign-in required`, `Waiting for update`, `Verifying installation`, `Indexing content`, or `Running`.

The Battle.net page remains available globally and opens automatically only for `ShowBattleNetInteraction`, install interaction, explicit `OPEN BATTLE.NET`, or explicit `SIGN IN`.

## Error handling
Network Offline routes to the existing network repair surface. Broken software bridge routes to the existing software repair surface. Launch cooldown remains authoritative. Failure events return the preparation pipeline to a stable decision rather than leaving a separate ad-hoc state.

## Compatibility
No new network transport, proxy, DNS rewriting, TLS weakening, credential automation, private Battle.net command protocol, or proprietary game redistribution is introduced. Existing v0.3.11 discovery, persistence, network probes, session supervision, update detection, install watcher, window hosting, and official launch functions remain canonical.

## Testing
Pure decision tests cover: offline network, missing client, sign-in intent, install intent, game already running, active update, unindexed install, ready game, and bridge failure cooldown. Launcher integration tests verify that PLAY no longer forces the Battle.net page when direct/background launch is possible, while INSTALL and SIGN IN still surface Battle.net interaction when required.
