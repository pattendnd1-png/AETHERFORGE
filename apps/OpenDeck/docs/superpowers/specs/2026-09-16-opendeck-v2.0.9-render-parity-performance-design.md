# OpenDeck+ 2.0.9 Render-Parity + Performance Design

**Status:** Design / acceptance contract — implementation begins only after this written spec is approved.

**Canonical baseline:** OpenDeck+ 2.0.8 (qualified + activated).

**Canonical visual reference:** `OpenDeck-v2.0.9-CANONICAL-UI-TARGET.png` at 1536×1024. This image is authoritative for overall composition, proportions, surface treatment, device presentation, navigation, Action Library, and configuration area.

## Goal

Make the actual OpenDeck+ application look like the approved render as closely as practical while matching or exceeding the responsiveness of the Windows Stream Deck application. A release does not qualify merely because source contracts, unit tests, or builds pass; visual and performance acceptance are independent blocking gates.

## Scope

2.0.9 is a UI/UX + rendering/performance closure release. It preserves all qualified 2.0.8 behavior: Stream Deck Plus HID runtime, Twitch device auth, Keys/Dials filtering, independent Press / Rotate Left / Rotate Right / Press+Rotate Left / Press+Rotate Right bindings, persistence, and existing action execution.

Dial Stacks are explicitly deferred to 2.0.10. No Dial Stack model or behavior is introduced in 2.0.9.

## Visual Architecture

### Window composition

At the 1536×1024 reference size, the app must preserve the approved render's hierarchy:

- Header: approximately 0–92 px high (9% of window height).
- Left navigation rail: approximately 0–238 px wide (15.5% of window width).
- Right Action Library: approximately x=1148–1520 (24% of window width).
- Main editor canvas: between the left rail and Action Library.
- Device presentation: centered in the upper main canvas, approximately x=335–1070 and y=110–675.
- Configuration area: directly below the device, approximately x=245–1140 and y=698–1000.

Bounding-box tolerance for the five primary regions is ±2% of window width/height at the reference size. Responsive layouts may scale, but the ratios and hierarchy must remain recognizable.

### Header

The header contains:

- OpenDeck+ identity and version at left.
- Device selector near left-center.
- Connected status immediately adjacent to device selection.
- Profile selector near center-right.
- Saved state, undo, redo, and settings controls at far right.

The header must not revert to the current sparse two-row Device/Profile form.

### Left navigation rail

The rail is always visually distinct from the center canvas and contains large icon+label entries:

- Buttons
- Dials
- Touch Strip
- Profiles
- Plugins
- Settings

The selected section uses the approved indigo/violet DragonGlass highlight. The rail footer contains compact OpenDeck+ version/open-source copy.

### Stream Deck Plus device presentation

The device must visually read as a physical Stream Deck Plus, not as unrelated rectangles and circles.

Required structure:

- One coherent rounded device body / bezel.
- 4×2 key grid with eight square key faces.
- Key icons are centered; labels sit inside each key face.
- A single continuous touch display below the keys, divided into four equal functional regions while visually remaining one screen.
- Four large rotary dials below the touch display.
- Each dial has a visible luminous ring, center cap, and label below.
- Dial colors / touch regions may differ by binding but remain within the approved violet/blue/cyan/amber/magenta visual language.

At 1536×1024:

- Key faces target ~120–132 px square with 14–24 px gaps.
- Touch display target ~640 px wide × 64–78 px high.
- Dials target ~84–98 px outer diameter.
- All four dials are evenly distributed under the four touch regions.

Element-size tolerance is ±8% at the reference size; spacing tolerance is ±10 px unless proportional scaling is active.

### Action Library

The right panel is a polished first-class pane, not a bare list.

It must include:

- `Action Library` heading.
- Search field at top.
- Keys / Dials segmented tabs.
- Collapsible action categories with iconography.
- Rows with action icons, labels, hover, focus, drag, and selected states.
- Scroll virtualization once the action catalog exceeds the first viewport.

The panel stays approximately 23–26% of total window width at desktop sizes.

### Configuration area

The configuration area sits directly beneath the device and is always contextual.

For a selected dial it contains:

- `Configure: Dial N` header.
- Dial selector / previous-next controls.
- Left interaction rail for Press, Rotate Left, Rotate Right, Press+Rotate Left, Press+Rotate Right.
- Assigned Action surface.
- Action-specific settings.

For keys/touch regions, the interaction rail and settings adapt to that control. The area must not be an empty generic panel.

### DragonGlass treatment

DragonGlass is the visual language, not a separate optional theme:

- very dark translucent/smoked surfaces
- soft background blur where the platform supports it
- subtle indigo/violet/cyan edge light
- minimal hard borders
- soft rounded corners
- pale near-white/light-lavender text
- high-contrast selection states
- no large flat opaque near-black rectangles unless required for a control face

## Visual Acceptance Gate

The release verifier must capture a deterministic screenshot at 1536×1024 using a seeded demo workspace matching the canonical image's content shape.

2.0.9 VISUAL=PASS requires all of the following:

1. Primary-region geometry within ±2% of the canonical reference.
2. Device sub-elements within the size/spacing tolerances above.
3. No current-2.0.8 sparse shell regressions: no tiny disconnected dial circles, no four independent touch-strip boxes, no empty generic inspector, no two-row sparse top controls.
4. Edge/structure similarity against the canonical render of at least 0.93 after masking dynamic text and icon glyph interiors.
5. Pixel/color similarity of at least 0.82 after masking dynamic text, icons, and OS window controls.
6. Human visual review confirms the app is recognizably the approved render rather than merely containing the same functional regions.

Automated similarity is necessary but not sufficient. Human visual approval remains a release gate for 2.0.9.

## Performance Architecture

The UI path must avoid blocking work on the renderer thread. Required strategies:

- memoized / localized React state so a single selection does not rerender the whole shell
- virtualized Action Library rows for large catalogs
- cached decoded icons and thumbnails
- deferred or background asset discovery
- debounced search with immediate local echo and fast filtered results
- Rust-side HID parsing and event normalization before crossing the Tauri boundary
- batched/coalesced high-frequency dial UI updates where appropriate without losing logical ticks
- no synchronous filesystem/network operations on the UI thread
- persisted writes queued asynchronously after immediate UI state commits

## Performance Acceptance Gate

Measurements are taken in a release build on the user's AetherForge/Garuda host with the Stream Deck Plus connected, after one warm-up run. Each interactive benchmark runs at least 100 samples unless otherwise stated. p95 and p99 are measured from the same sample set.

### Startup

- Warm start to first interactive frame: p95 ≤ 650 ms.
- Cold start to first interactive frame: p95 ≤ 1.2 s.
- First interaction after launch must not block on asset discovery, plugin enumeration, or network access.

### Core UI latency

- Sidebar/tab selection to visible selected state: p95 ≤ 35 ms, p99 ≤ 60 ms.
- Key/dial/touch selection to configuration-pane update: p95 ≤ 50 ms, p99 ≤ 80 ms.
- Keys↔Dials Action Library tab switch: p95 ≤ 35 ms, p99 ≤ 60 ms.
- Action assignment drop/click to visible binding update: p95 ≤ 60 ms, p99 ≤ 100 ms.
- Profile switch to usable editor state for a typical profile: p95 ≤ 120 ms, p99 ≤ 200 ms.

### Search and large catalogs

With 5,000 synthetic actions loaded:

- keystroke to filtered result paint: p95 ≤ 70 ms, p99 ≤ 110 ms
- no single renderer long task > 50 ms during search
- Action Library memory grows sublinearly through virtualization; all 5,000 rows must not be mounted simultaneously

### Animation / frame pacing

On a 60 Hz display:

- ≥95% of frames during scrolling, dragging, resizing, and selection animations complete within 16.7 ms.
- ≥99% complete within 33.3 ms.
- No frame > 50 ms during a 10-second drag/drop benchmark.

On higher-refresh displays, the app should track the display refresh where platform compositor/WebView behavior permits; the 60 Hz budgets remain the release floor.

### Hardware latency

Measured from decoded HID report timestamp inside OpenDeck:

- HID decode → action-dispatch queue: p95 ≤ 10 ms, p99 ≤ 16 ms.
- HID decode → visible dial ring/touch-strip feedback: p95 ≤ 25 ms, p99 ≤ 40 ms.
- Dial rotation must not visibly lag behind physical input during sustained rotation.
- Press and Press+Rotate state transitions must update on the same report cycle and must never be collapsed into ordinary rotation.

### Persistence latency

- UI state updates immediately before disk persistence completes.
- Local persistence enqueue: p95 ≤ 10 ms.
- Typical workspace write completion: p95 ≤ 150 ms without blocking interaction.

### Idle efficiency

After 60 seconds idle with the standard demo workspace:

- OpenDeck-related idle CPU average ≤ 1.5% of one logical CPU core.
- Total OpenDeck process-tree resident memory target ≤ 300 MiB.
- No periodic polling loop faster than 10 Hz without an active hardware/animation reason.

Memory is a target gate: exceeding it requires an explicit measured justification and user approval; latency/frame-time gates are hard blockers.

## Windows Responsiveness Comparison

Absolute gates above are always required. If a same-workload Windows Stream Deck reference measurement is available on comparable hardware, OpenDeck+ 2.0.9 additionally requires:

- no core interactive latency metric more than 10% slower at p95
- no hardware-feedback metric more than 10% slower at p95
- target: at least 3 of the 5 core UI latency metrics are ≥10% faster than the Windows reference

A missing Windows reference does not waive the absolute gates.

## Regression Gates

2.0.9 must also retain:

- frontend tests
- frontend lint with zero warnings
- frontend production build
- `cargo fmt --all -- --check`
- `cargo check --workspace --all-targets --all-features --locked`
- strict Clippy with `-D warnings`
- Rust tests
- release build
- Tauri build
- Stream Deck Plus OS probe
- Twitch device-flow polling/cancel/expiry contracts
- dial Press / Rotate Left / Rotate Right / Press+Rotate Left / Press+Rotate Right contracts
- no background service or autostart regression

## Cutover Policy

OpenDeck+ 2.0.8 remains the active qualified binary until every 2.0.9 functional, visual, performance, build, and hardware gate is green. A visually failing or latency-failing 2.0.9 candidate is not eligible for activation even if all unit/build gates pass.
