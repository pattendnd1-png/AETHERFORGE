# OpenDeck v2.0.3 Windows-Parity + Stream Deck + Hardware Runtime Design

**Date:** 2026-09-15
**Baseline:** OpenDeck v2.0.2 host-qualified and active; source commit `cf19318008d95df97a5469db21747f2233fe6181`.
**Target:** OpenDeck v2.0.3.
**Primary hardware:** Elgato Stream Deck + model `20GBD9901`, USB VID `0x0FD9`, PID `0x0084`.
**UI target:** Match the current Windows Stream Deck desktop workflow and density closely while remaining Linux-native and clean-room. Do not copy proprietary binaries or protected artwork.

## Problem

OpenDeck v2.0.2 qualifies as software but does not yet own or drive the physical Stream Deck + HID device. The visible editor also diverges from the Windows Stream Deck desktop workflow: the action library is visually too low/flat, the device canvas is undersized, the property inspector is compressed, and device state is not represented clearly in the top chrome. The result can compile cleanly while the physical device appears inert.

## Goals

1. Make the physical Stream Deck + respond while OpenDeck is running: discover/hotplug the device, receive 8 key events, 4 dial push/rotate events, and touch-strip tap/press/flick events.
2. Render the active OpenDeck page to the hardware: 8 button images and the 800×100 touch strip, with safe fallback rendering when an asset cannot be decoded.
3. Route hardware input through the existing OpenDeck action execution model so physical input and GUI `Test Action` share behavior.
4. Rebuild the desktop shell around the Windows Stream Deck interaction model: large device canvas on the left, full-height action library on the right, page controls directly beneath the device, and a substantial property inspector below the device.
5. Show explicit hardware state in the UI: disconnected, connecting, connected, permission denied, and I/O error. Do not silently pretend a device is connected.
6. Preserve v2.0.2 data and rollback. Keep background services and autostart disabled.

## Non-Goals for v2.0.3

- Do not add a systemd service or always-on daemon.
- Do not auto-start OBS streaming or recording during tests, install, or qualification.
- Do not implement every Stream Deck model in this release. The protocol boundary must be extensible, but Stream Deck + is the acceptance target.
- Do not copy the Windows app's assets, fonts, binaries, or proprietary plugin implementation.
- Do not replace the Rust/Tauri architecture with Electron or a Node sidecar.

## External Protocol Basis

Elgato's current public Stream Deck HID API documents Stream Deck + as VID `0x0FD9`, PID `0x0084`, with a 4×2 keypad, four encoders, 120×120 button images, and an 800×100 touch-strip image. Input report `0x01` uses command `0x00` for keys, `0x02` for touch activity, and `0x03` for encoder changes. Output report `0x02` uses command `0x07` for button images and `0x0B` for the full touch-strip image. Output reports are zero-padded to 1024 bytes; input polling should use timed reads. Images are JPEG and do not require rotation on Stream Deck +.

The implementation uses only these public protocol facts and the Rust `hidapi` abstraction; no Elgato binary is bundled or executed.

## Architecture

### 1. Rust-owned device service

Add `src-tauri/src/streamdeck/` with four focused units:

- `protocol.rs`: pure encode/decode functions for Stream Deck + HID reports. Key and dial button reports decode to complete device-state vectors; `runtime.rs` diffs those vectors into edge events so reconnect/reset state remains centralized. No filesystem, Tauri, or HID handles. Fully unit-testable without hardware.
- `render.rs`: converts OpenDeck `Appearance` + asset records into JPEG button/touch-strip frames. It owns image resizing/composition and deterministic safe fallbacks.
- `runtime.rs`: owns the HID handle on one worker thread, performs 50ms timed reads, hotplug retry, output writes, and command-channel processing.
- `mod.rs`: Tauri-facing service state, serializable status/events, commands, and startup/shutdown glue.

Only the worker thread owns `HidDevice`; UI/Tauri commands communicate through an `mpsc` command channel. This prevents competing HID handles and makes unplug/replug recovery deterministic.

### 2. Hardware event contract

Rust emits a single Tauri event name, `opendeck://hardware-input`, with payload variants:

- `keyDown { index }`
- `keyUp { index }`
- `dialDown { index }`
- `dialUp { index }`
- `dialRotate { index, ticks }`
- `touchTap { x, y, region }`
- `touchPress { x, y, region }`
- `touchFlick { startX, startY, endX, endY, region }`

Touch `region` is derived as `min(3, x * 4 / 800)`. Flicks remain available in the payload even though the v2.0.3 action mapper only uses the start region unless a future gesture-specific action exists.

Rust emits `opendeck://hardware-status` whenever state changes. The frontend can also query status synchronously through `streamdeck_status`.

### 3. Physical input mapping

The frontend maps events to the current active page:

- key down → key `press` action
- dial down → dial `press` action
- dial rotate positive → dial `rotateRight`; negative → `rotateLeft`, executed once per tick with a bounded maximum of 16 executions per report
- touch tap → touch-region `touch` action
- touch long press → touch-region `longPress` when configured, otherwise `touch`
- key/dial release resets the runtime input-state latch and does not execute a second action

Hardware-triggered OBS Stream/Record actions must use the configured action directly and must never be fired by qualification. Because a physical key press is itself explicit user intent, runtime hardware execution does not show the GUI `Test Action` confirmation dialog. The existing `Test Action` confirmation remains unchanged.

### 4. Hardware rendering

On connect and whenever the workspace, active profile, active page, or relevant asset changes, the frontend sends the current workspace to `streamdeck_sync_workspace`.

Rust resolves the active profile/page and renders:

- eight 120×120 JPEG button images
- one 800×100 JPEG touch-strip image divided into four logical 200px regions

Rendering order is background color → optional background asset → optional icon asset → compact title. To avoid a bundled proprietary font, v2.0.3 uses a small built-in bitmap glyph renderer for ASCII titles. Unsupported characters are skipped rather than corrupting the frame.

If image decoding fails, the renderer keeps the background and title and reports the asset warning without disconnecting hardware.

### 5. Desktop shell parity

The top bar remains compact and contains device selector/status, profile selector/management, undo/redo, Connections, and Marketplace.

The main workspace is a two-column grid:

- left: device stage, page navigator, resize divider, property inspector
- right: full-height action library with search and grouped actions

The device stage scales the Stream Deck + representation up materially from v2.0.2 while preserving 4×2 keys, touch strip, and four dials. Action-library width remains resizable. Property-inspector height remains resizable. At narrow application widths, the action library remains on the right and gains its own scroll instead of moving below the device.

The device selector shows the real hardware name when connected. A compact status pill uses text and state, not color alone.

### 6. Linux permissions

OpenDeck ships a udev rules file under `packaging/70-opendeck-streamdeck.rules` granting the active logged-in desktop session access to Stream Deck + USB/hidraw nodes for vendor `0fd9`, product `0084`, via `TAG+="uaccess"`. The host activator installs it only when running with sufficient privileges or when the user explicitly invokes the provided install command. Build/qualification never silently escalates privileges.

If the device is visible but cannot be opened, the UI displays a permission-specific message with the exact udev install command.

### 7. Lifecycle and safety

- Device runtime starts with the OpenDeck app and stops when the app exits.
- No systemd user service and no autostart entry are created.
- On clean shutdown, runtime sends the device `Show Logo` feature report before closing when the handle is healthy.
- On disconnect, the worker drops the handle, reports the I/O failure, and retries enumeration every second until it can report connected or not-connected state again.
- A failed frame write does not crash the app; it transitions to `ioError`, drops the handle, and returns to reconnect polling.
- v2.0.2 remains the rollback target until all v2.0.3 gates pass.

## Data and API Changes

Frontend bridge additions:

```ts
streamdeckStatus(): Promise<StreamDeckStatus>
streamdeckSyncWorkspace(workspace: Workspace): Promise<void>
streamdeckSetBrightness(percent: number): Promise<void>
```

Frontend event payload types live in `src/types.ts`.

Rust commands:

```rust
#[tauri::command]
fn streamdeck_status(state: State<'_, StreamDeckService>) -> StreamDeckStatus;

#[tauri::command]
fn streamdeck_sync_workspace(
    workspace: editor::Workspace,
    state: State<'_, StreamDeckService>,
) -> Result<(), String>;

#[tauri::command]
fn streamdeck_set_brightness(
    percent: u8,
    state: State<'_, StreamDeckService>,
) -> Result<(), String>;
```

## Testing

### Pure Rust tests

- decode key press/release reports
- decode dial button and signed rotation reports
- decode touch tap/press/flick reports and region mapping
- encode 1024-byte button-image chunks with correct final flag, chunk size, and index
- encode touch-strip chunks
- encode brightness and show-logo feature reports
- render correct 120×120 and 800×100 JPEG dimensions
- workspace-to-frame resolution for eight keys/four touch regions

### Frontend tests

- Windows-parity shell places action library in the right column and property inspector beneath device stage
- hardware status renders in top bar
- key/dial/touch Tauri events resolve to the correct control and interaction
- release events do not execute actions
- multi-tick rotations are bounded
- workspace changes request a device sync
- no qualification/test path automatically calls OBS Stream/Record

### Qualification gates

Required before activation:

```text
npm test
npm run lint
npm run build
cargo fmt --all -- --check
cargo check --workspace --all-targets --all-features
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-targets --all-features
cargo build --workspace --release
npm run tauri build
```

Hardware runtime acceptance is separate from compile qualification and requires the physical Stream Deck +:

```text
DEVICE_ENUMERATION=PASS
KEY_INPUT_8=PASS
DIAL_PRESS_4=PASS
DIAL_ROTATE_4=PASS
TOUCH_REGIONS_4=PASS
KEY_IMAGE_OUTPUT_8=PASS
TOUCH_STRIP_OUTPUT=PASS
HOTPLUG_RECONNECT=PASS
WORKSPACE_ACTION_DISPATCH=PASS
```

## Acceptance

v2.0.3 may activate only when all software gates pass. Physical-device support is called runtime-qualified only after the physical acceptance checklist passes on the user's Stream Deck +. If the software gates pass but hardware acceptance has not run, the release must say so explicitly instead of claiming the device works.
