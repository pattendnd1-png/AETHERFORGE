# OpenDeck+ 2.0.21 Adaptive Unified Touch Strip Design

**Status:** Approved design, implementation target.

**Baseline:** OpenDeck+ 2.0.20 rustfmt closure state carried forward from the 2.0.19 host evidence. The active installed baseline remains 2.0.8 until this candidate fully qualifies.

## Goal

Treat the Stream Deck+ 800×100 touch display as either four independent 200×100 regions or one seamless 800×100 display/touch surface, and allow the presentation to switch automatically by active application/use while retaining a manual override.

## User-visible behavior

Each page has a Touch Strip mode:

- `segmented`: four independent touch regions, matching existing behavior.
- `unified`: one full-width 800×100 visual surface and one logical touch control.
- `adaptive`: resolve to segmented or unified from the active application identifier, with a configurable fallback.

The editor exposes mode configuration only when a touch control is selected, so the canonical Dial-selected 1536×1024 qualification render does not change.

## Durable model

`Page` gains a `touchStrip` object with:

- `mode`: `segmented | unified | adaptive`
- `adaptiveFallback`: `segmented | unified`
- `adaptiveRules`: ordered `{ pattern, presentation }[]`
- `unifiedSlot`: a durable `ControlSlot` with kind `touch`

Old workspaces remain schema-version 1 compatible. Rust deserialization supplies defaults when `touchStrip` is absent, so no destructive migration is required.

## Mode resolution

`resolveTouchStripPresentation(page, activeApplicationId)` is the canonical pure resolver in the frontend. Rules are case-insensitive substring matches against the application identifier. First matching rule wins. `segmented` and `unified` modes ignore rules.

Qualification mode does not poll the desktop and uses the deterministic page configuration from the qualification workspace.

## Active-application context

Linux runtime context is best-effort and non-fatal:

1. `OPENDECK_ACTIVE_APP` environment override, used by qualification/tests.
2. `kdotool getactivewindow getwindowclassname` on KDE Wayland when available.
3. `xdotool getactivewindow getwindowclassname` for X11/XWayland fallback.
4. `null` when no provider is available.

The frontend polls only while an active page uses `adaptive`, at 750 ms. A change triggers a hardware resync but does not mutate or autosave the workspace.

## Editor rendering

`DeviceEditor` receives the effective touch presentation.

- Segmented: render the existing four `TouchControl`s.
- Unified: render one full-width `UnifiedTouchControl` backed by `page.touchStrip.unifiedSlot`.

The outer physical touch-display bezel and canonical geometry remain unchanged.

## Hardware rendering

The Rust renderer already emits one 800×100 hardware image. It is extended to choose:

- segmented: composite the four existing 200×100 regions into the 800×100 frame;
- unified: render `unifiedSlot` directly at 800×100.

The resolved presentation and current active app id are passed with each workspace sync so desktop preview and hardware use the same decision.

## Hardware input

The HID parser continues reporting exact touch coordinates. `resolveHardwareExecutions` accepts the effective presentation:

- segmented routes by `event.region` to one of four region slots;
- unified routes every touch event to `unifiedSlot` and preserves the raw coordinate/gesture data in `HardwareExecution.touch`.

Unified touch context includes normalized X/Y plus start/end coordinates for flicks. Existing actions may ignore this context; future scrubber/waveform actions can consume it without changing HID routing again.

## Editing and remapping

The unified slot uses the same Action/Appearance/States workflow as every other control. Its `touch` and `longPress` bindings are fully remappable. Segmented bindings remain untouched and immediately return when the page switches back to segmented mode.

## Compatibility and safety

- No background daemon or autostart.
- No change to key/dial mappings, encoder press+rotate semantics, Twitch, OBS, persistence timing, or canonical canvas-fit behavior.
- No physical input synthesis during qualification.
- 2.0.8 remains active until host gates and visual review pass.
- Dial Stacks move to 2.0.22 so 2.0.21 remains focused on touch-strip architecture.
