# OpenDeck v2.0.1 Full Customization Editor Design

**Date:** 2026-09-14<br>
**Baseline:** OpenDeck v2.0.0 CLEAN, host-qualified through frontend tests/lint/build, strict Clippy, Rust tests, release build, and Tauri build.<br>
**Target:** OpenDeck v2.0.1<br>
**UI policy:** Windows Stream Deck workflow/density first; no DragonGlass in this release.<br>
**Runtime policy:** no background daemon, no autostart, no OBS auto-start, no public-stream test.

## 1. Problem statement

The v2.0.0 CLEAN baseline proved the new build, installation, OBS connection, Twitch device authorization, Marketplace handoff, and a Windows-like editor shell. It is not yet a serious customization editor.

The current frontend is intentionally small: one `App.tsx`, eight key slots, one selected key index, a static action list, and best-effort `localStorage` persistence. Dials and touch-strip regions are visual placeholders rather than editable controls. The Property Inspector only exposes action-specific title/scene/input fields. There is no durable profile/page/folder model, appearance model, asset library, per-state styling, drag/drop editor, undo/redo history, or typed action-inspector contract.

The result looks closer to Stream Deck than earlier versions, but it feels oversized and static. v2.0.1 replaces that prototype editor model with a compact, stateful customization workspace.

## 2. Goals

v2.0.1 must provide a real customization system for Stream Deck Plus-style editing:

- compact Windows-style editor geometry and control density;
- editable 8 keys, 4 dials, and 4 touch-strip regions;
- drag/drop action assignment and control reordering/copying;
- title, icon, background, typography, alignment, and visibility controls;
- per-state appearance for default/on/active states;
- dial rotate-left, rotate-right, press, and optional touch behaviors;
- touch-strip label/icon/background/state presentation and touch actions;
- profiles, pages, and folders as persisted first-class objects;
- contextual Property Inspector driven by selected control and selected action;
- user-owned icon packs and imported custom images in an asset browser;
- Rust-owned, versioned, atomic persistence instead of authoritative `localStorage`;
- undo/redo for editor mutations;
- existing OBS, Twitch account, and Marketplace surfaces preserved;
- clean extension points for future Marketplace plugins/actions and hardware transport.

## 3. Non-goals for v2.0.1

To keep the editor release bounded and testable, v2.0.1 does not:

- apply DragonGlass styling;
- add a persistent background daemon or autostart service;
- execute proprietary Windows/macOS plugin binaries;
- collect Elgato account passwords or depend on undocumented private account endpoints;
- claim binary-compatible execution of proprietary Marketplace plugins;
- redesign OBS/Twitch authentication protocols that already work;
- replace the clean-room action/runtime model with vendor binaries or protected artwork.

Marketplace packages may contribute imported assets/metadata only when the package format is understood and safe to parse. Unsupported executable/plugin payloads remain marked unsupported rather than guessed at.

## 4. UI density and workspace geometry

The shell remains recognizably Windows Stream Deck rather than AetherForge-themed.

### 4.1 Top bar

Target height: approximately 42–46 px.

Contains:

- device selector;
- profile selector;
- profile add/rename/duplicate controls;
- undo/redo;
- Accounts/Connections;
- Marketplace.

Selectors use compact 28–30 px controls. Labels that do not add meaning are removed in favor of inline accessible labels/tooltips.

### 4.2 Main workspace

Three functional regions:

1. **Center Device Editor** — dominant area.
2. **Right Action Library** — default width about 280 px, resizable approximately 240–360 px.
3. **Bottom Property Inspector** — default height about 220 px, resizable approximately 170–320 px.

The Action Library and Inspector may collapse independently. Their sizes persist in editor preferences.

### 4.3 Device canvas

The current oversized framed mock-device is replaced by a tighter device preview:

- keys use smaller gaps and lighter framing;
- selected control gets one clear accent outline rather than multiple heavy borders;
- touch strip is segmented into four selectable regions;
- dials are selectable controls with compact labels and state indicators;
- page navigation sits directly below the device and includes add/delete/duplicate page controls;
- zoom is available for the editor canvas without altering saved device content.

No decorative shadow or padding should consume space needed by the actual editor.

## 5. Domain model

The editor state becomes independent of React component structure.

```text
Workspace
├── schema_version
├── active_device_id
├── devices[]
├── profiles[]
├── assets[]
└── preferences

Profile
├── id
├── name
├── device_id
├── pages[]
├── active_page_id
└── app_match rules (future-compatible field)

Page
├── id
├── name
├── slots
│   ├── keys[8]
│   ├── dials[4]
│   └── touch_regions[4]
└── folder/navigation metadata

ControlSlot
├── id
├── kind: key | dial | touch
├── action_bindings
├── appearance
├── states
└── folder_target (optional)
```

All IDs are stable UUIDs. Index/position is presentation metadata, not identity.

### 5.1 Action bindings

A control can expose the interactions appropriate to its kind.

**Key**

- press;
- optional long-press;
- optional alternate/toggle state.

**Dial**

- rotate left;
- rotate right;
- press;
- optional long press/touch when supported.

**Touch region**

- tap/touch;
- optional swipe/hold fields reserved for transport support.

Each binding stores an `ActionInstance` containing an action definition ID and a typed JSON configuration payload.

### 5.2 Appearance

`Appearance` contains:

- title text;
- title visibility;
- font family;
- font size;
- font weight;
- text color;
- horizontal/vertical alignment;
- icon asset reference;
- background asset reference;
- background color;
- icon scale/fit mode;
- icon opacity;
- optional title offset.

Appearance is previewed immediately in the device editor.

### 5.3 States

Controls have a base/default state plus named states. Built-in toggles use at least `default` and `active`. Every state may override appearance fields without duplicating the entire base appearance.

This supports mute/unmute, recording on/off, streaming on/off, folder state, and future action-specific state visualization.

## 6. Action registry and contextual inspector

The static `ACTION_LIBRARY` array becomes an action registry.

```text
ActionDefinition
├── id
├── service/group
├── display_name
├── supported_control_kinds
├── default_instance
├── inspector_schema
└── execute capability
```

The initial registry keeps the existing built-ins:

- OBS Scene;
- OBS Toggle Stream;
- OBS Toggle Record;
- OBS Toggle Input Mute;
- Open Elgato Marketplace.

It also provides editor-native actions required for customization/navigation:

- Folder;
- Next Page;
- Previous Page;
- Switch Profile;
- No-op/blank.

The registry is data-driven enough that later Marketplace-compatible actions can provide inspector fields without adding a custom React form for every action.

### 6.1 Inspector tabs

The bottom Property Inspector contains compact tabs:

**Action**

- action-specific configuration;
- interaction binding selector for dials/touch regions;
- Test Action button where safe;
- remove/clear binding.

**Appearance**

- title;
- icon/background picker;
- font family/size/weight;
- text color;
- alignment;
- fit/scale;
- visibility.

**States**

- state selector;
- per-state overrides;
- copy appearance from default;
- reset state override.

The inspector never shows irrelevant fields. Selecting a dial interaction such as Rotate Left edits that binding without changing Press or Rotate Right.

## 7. Drag/drop and direct manipulation

The editor supports the expected direct workflows:

- drag an Action Library item onto any compatible control;
- click an Action Library item, then click a compatible control as an accessibility fallback;
- drag one control onto another to move it;
- modifier-drag/copy command duplicates a control configuration;
- drop an image file onto a key/touch region to import it and set it as the icon/background according to context;
- drag assets from the Asset Browser onto controls;
- incompatible drops are rejected with a clear non-modal message.

A drag operation produces one undoable mutation rather than many intermediate history entries.

## 8. Profiles, pages, and folders

### 8.1 Profiles

Profiles are persisted, not hard-coded options. Users can:

- create;
- rename;
- duplicate;
- delete with confirmation;
- switch from the top bar;
- export/import in OpenDeck’s versioned format.

At least one profile must always exist.

### 8.2 Pages

Every profile owns one or more pages. Users can:

- add;
- rename;
- duplicate;
- reorder;
- delete when more than one exists;
- navigate through the Plus page controls.

### 8.3 Folders

A Folder is an editor-native action/navigation target. Activating it opens a child page collection or folder page and supplies an automatic Back action slot/gesture where appropriate.

Folders are represented in the persisted model rather than encoded as magic action labels.

## 9. Asset library

### 9.1 Sources

The Asset Browser indexes:

- preserved OpenDeck icon packs under the existing local icon-pack root;
- images imported by the user;
- compatible Marketplace-downloaded icon packs;
- OpenDeck-owned built-in neutral assets.

The previously preserved user icon packs remain user-owned inputs and are not redistributed automatically.

### 9.2 Storage

Imported custom assets are copied into an OpenDeck-managed asset directory rather than referencing arbitrary external paths.

Suggested layout:

```text
~/.config/opendeck-v2/
├── editor/
│   ├── workspace.json
│   ├── workspace.backup.json
│   └── migration.json
└── assets/
    ├── imported/
    └── index.json
```

Asset IDs are content-addressed or UUID-based and stored in editor state by reference. Duplicate imports should not create duplicate binary copies when their hash matches.

Images are validated before indexing. Broken/missing assets render a recoverable placeholder and never corrupt the workspace.

## 10. Persistence ownership

Rust becomes authoritative for durable editor state.

New Tauri commands provide a narrow persistence boundary:

- `editor_load_workspace`;
- `editor_save_workspace`;
- `editor_import_asset`;
- `editor_list_assets`;
- `editor_export_profile`;
- `editor_import_profile`.

Writes use:

1. serialize and validate;
2. write a temporary file in the same directory;
3. fsync where practical;
4. rename atomically;
5. retain the last known-good backup.

The frontend owns transient selection/drag/modal state but not the durable source of truth.

### 10.1 v2.0.0 localStorage migration

On first v2.0.1 launch:

1. Rust reports no migrated workspace or reports migration pending.
2. Frontend reads `opendeck-v2.keys` from localStorage once.
3. Valid eight-key data is converted into the default profile/page key slots.
4. Frontend sends the converted workspace to Rust.
5. Rust validates and saves it atomically.
6. Only after Rust acknowledges success does the frontend remove the old localStorage key and record migration completion.

Invalid or unavailable localStorage does not block launch; the editor creates an empty default workspace.

## 11. State management and undo/redo

React components do not directly mutate nested workspace objects. Editor operations are explicit commands/reducer actions, for example:

- `ASSIGN_ACTION`;
- `UPDATE_APPEARANCE`;
- `MOVE_CONTROL`;
- `COPY_CONTROL`;
- `ADD_PAGE`;
- `DELETE_PAGE`;
- `CREATE_PROFILE`;
- `IMPORT_ASSET`.

Undo/redo keeps a bounded in-memory history of editor mutations. Selection changes, modal opening, service connection status, and harmless hover/drag-preview state do not enter history.

Autosave is debounced after mutations. An explicit dirty/saving/saved/error indicator lives in the compact status area.

## 12. Component boundaries

`App.tsx` becomes a composition root rather than the entire application.

Proposed frontend structure:

```text
src/
├── app/
│   ├── App.tsx
│   └── editor-store.ts
├── model/
│   ├── workspace.ts
│   ├── actions.ts
│   └── migration.ts
├── components/
│   ├── TopBar.tsx
│   ├── DeviceEditor.tsx
│   ├── KeyControl.tsx
│   ├── DialControl.tsx
│   ├── TouchControl.tsx
│   ├── ActionLibrary.tsx
│   ├── PropertyInspector.tsx
│   ├── AssetBrowser.tsx
│   ├── PageNavigator.tsx
│   └── ProfileManager.tsx
├── inspector/
│   ├── ActionInspector.tsx
│   ├── AppearanceInspector.tsx
│   └── StatesInspector.tsx
└── bridge.ts
```

The Rust module is split similarly so persistence, assets, services, and Tauri command wiring are not all in one `lib.rs`.

## 13. Service behavior

Existing OBS/Twitch/Marketplace behaviors are preserved.

- OBS connection settings remain in Rust private config.
- Twitch Device Code Flow remains unchanged.
- Marketplace continues to open the official site and scan local compatible downloads.
- Editor service actions refer to connection state but do not automatically start OBS or begin a stream.
- Test Action for stream/record operations requires the same explicit user click as today; qualification tests never perform a public stream.

## 14. Hardware/application boundary

The editor model must not depend on a specific HID implementation. A future/parallel device transport consumes normalized rendered control state:

```text
RenderedDeviceState
├── key frames
├── touch-strip frame/regions
├── dial labels/state metadata
└── input bindings
```

For v2.0.1, the software editor and persistence model are authoritative and must render every customization accurately in the on-screen Plus preview. The transport interface is defined now so connected-device synchronization can be added without rewriting the editor model or persistence schema.

No background daemon is introduced in this release. If live hardware transport is added during v2.0.1 implementation, it must be owned by the foreground Studio process and must preserve the no-background-services policy.

## 15. Error handling

- malformed workspace JSON: load last known-good backup; if none, create default workspace and surface a non-destructive warning;
- failed autosave: retain dirty state, show error, permit retry; never discard current editor state;
- missing asset: show placeholder and allow replacement/removal;
- incompatible action/control drop: reject without mutating state;
- service disconnected: inspector remains editable; execution reports connection error;
- failed migration: leave original localStorage untouched and retry later;
- failed profile import: do not partially merge; validate first, then commit atomically.

## 16. Testing and release gates

### Frontend unit/component tests

Required coverage includes:

- 8 keys, 4 dials, 4 touch regions are selectable;
- Action Library drag/drop assignment;
- appearance edits immediately update preview;
- state-specific appearance overrides;
- dial left/right/press bindings remain independent;
- touch-region configuration remains independent;
- profile/page/folder CRUD;
- move/copy control operations;
- undo/redo;
- contextual inspector field selection;
- storage migration handoff;
- panel density/collapse state behavior;
- asset selection/import UI;
- service actions remain available.

### Rust tests

Required coverage includes:

- workspace schema serialization/deserialization;
- validation and schema version rejection/migration;
- atomic save and backup recovery;
- asset hash/index/import behavior;
- invalid image rejection;
- profile import/export validation;
- path traversal rejection;
- existing OBS/Twitch tests remain green.

### Contract/integration gates

The v2.0.1 release may be called PASS only after:

- `npm test`;
- ESLint with zero warnings;
- TypeScript/Vite production build;
- `cargo fmt --check`;
- `cargo check --workspace --all-targets --all-features --locked`;
- strict `cargo clippy ... -- -D warnings`;
- full Rust tests;
- release build;
- Tauri build;
- source-package hygiene contract;
- editor schema/persistence contract;
- no background service/autostart contract;
- migration regression test from v2.0.0 eight-key localStorage state.

No release artifact is handed off with known compiler/Clippy warnings or with a partially migrated workspace.

## 17. Implementation order

The implementation should proceed in dependency order rather than visual patch order:

1. domain types and reducer operations;
2. Rust workspace persistence and migration command boundary;
3. componentized compact editor shell;
4. keys/dials/touch selection and previews;
5. contextual inspector and action registry;
6. appearance/state customization;
7. profiles/pages/folders;
8. asset browser/import/icon-pack indexing;
9. drag/drop and control move/copy;
10. undo/redo/autosave/status;
11. existing OBS/Twitch/Marketplace regression integration;
12. final density/geometry parity pass;
13. package/release verification.

This order prevents styling work from being repeatedly rewritten while the state model changes.

## 18. Acceptance criteria

v2.0.1 is acceptable when a user can launch OpenDeck and, without editing files manually:

- create/switch profiles and pages;
- select any of the 8 keys, 4 dials, or 4 touch regions;
- assign compatible actions using drag/drop or click assignment;
- configure the appropriate interaction for that control;
- change title/icon/background/font/color/alignment;
- define active/default visual states;
- use existing icon packs or imported custom images;
- create folders/navigation controls;
- move/copy controls;
- undo/redo edits;
- close/reopen OpenDeck and recover the same workspace from Rust persistence;
- retain existing OBS/Twitch/Marketplace functionality;
- experience a materially tighter, less clunky Windows Stream Deck-style workspace than v2.0.0.

The design must remain clean-room, Linux-native, and independent of proprietary vendor binaries.
