# OpenDeck v2.0.3 Windows-Parity + Hardware Runtime Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make OpenDeck v2.0.3 closely follow the Windows Stream Deck editor workflow and directly drive the user's Stream Deck + hardware while the app is running.

**Architecture:** Keep Tauri/Rust as the authority. A single Rust worker thread owns the HID handle and communicates through a command channel; pure protocol/render modules stay independently testable. The React editor listens for typed Tauri hardware events and routes them through the existing action executor, while workspace changes are rendered back to the deck.

**Tech Stack:** Rust 1.98.1, Tauri 2.8, `hidapi` 2.6.7 (`linux-native-basic-udev`), `image` 0.25 with JPEG/PNG, React 19, TypeScript 5.9, Vitest/Testing Library.

**Spec:** `docs/superpowers/specs/2026-09-15-opendeck-v2.0.3-windows-parity-hardware-design.md`

## Global Constraints

- Target version is exactly `2.0.3`.
- Baseline is host-qualified OpenDeck v2.0.2 commit `cf19318008d95df97a5469db21747f2233fe6181`.
- Primary device is Stream Deck + model `20GBD9901`, VID `0x0FD9`, PID `0x0084`.
- No proprietary Elgato binaries or protected artwork.
- No background service and no autostart.
- Qualification must never start OBS streaming or recording.
- Preserve v2.0.2 as rollback until every v2.0.3 software gate passes.
